# Phase 2.2 정본 개체 참조 무결성

## 장애 조사

소유자 보고에 따르면 ChatKHU Gateway의 gpt-6.2-sol Responses 요청은 출력 4,926토큰·추론 0토큰으로 응답했고, 이후 앱의 그래프 참조 검사에서 거절됐다. 당시 제공자 원문을 검사하지 않았다. 기존 앱은 프롬프트와 거절 원문을 보관하지 않으며, 저장된 실패 실행 기록만으로 모델이 사용한 문자열이나 의도를 복원할 수 없다.

Phase 1의 새 프로젝트는 빈 characters·factions 배열을 만든다. 소재와 후보를 편집하고 이야기를 승인하면 Narrative에는 안정적인 이야기 ID, 원천 후보 ID, 선택한 산문과 승인 상태가 남는다. 산문 속 인물·세력까지 등록되는 절차는 없었다. 합성 예시처럼 정본 인물·세력이 이미 들어 있는 프로젝트만 해당 ID를 제공할 수 있었다.

기존 시나리오 요청은 현재 인물·세력 배열을 보냈지만 닫힌 응답 스키마는 새 인물·세력을 선언할 필드를 제공하지 않았다. 정규화는 새 퀘스트·장소의 상태 키를 재작성했고 인물·세력 소속이나 새 아이템·결정·플래그를 통합할 수 없었다. 검증기가 미등록·다른 유형 참조를 거절한 것은 의도한 동작이다. 당시 어떤 참조가 이 중 어느 경우였는지는 미확정이다.

## 재현과 수정

한국어 합성 예제에서 수문지기와 구호회 선언 두 개만 뺀 뒤 전체 생성 API로 제출했다. HTTP 502와 개별 오류 23개(인물 12, 세력 11)가 나왔다. 장면과 퀘스트의 characterIds·factionIds, 조건과 결과의 키에서 같은 문제가 반복됐다. 두 선언이 있는 응답은 HTTP 200으로 검토 제안이 됐다. 3장, 메인·사이드 퀘스트 각 1개, 새 장소 1개, 아이템·결정·플래그 각 1개를 포함한다. 결정론적 탐색은 상태 9개에서 공개·봉인 두 결말의 경로를 각각 확인했다. 실제 소유자의 이야기를 복사한 예제가 아니다. [한국어 합성 픽스처와 API 검사](../backend/tests/test_scenario_entities.py)

- **등록** — 승인된 Narrative에서 기존 식별자를 확인하고 인물·소속, 세력, 아이템·유물, 결정, 플래그를 수동 등록할 수 있다. 산문만 있는 이야기도 바로 생성할 수 있다. 생성기가 새 인물과 장소를 도입하면 설계자가 제안 화면에서 이름·ID·소속·사용처를 함께 검토한다.
- **전송과 검증** — 입력의 inventory는 재사용 가능한 개체를 유형별로 구분한다. 교체할 그래프의 기존 퀘스트는 맥락으로 제공하고 새 그래프에 사용할 퀘스트는 선언한다. 서버는 응답 안에서 유일한 임시 ID를 정본 ID로 대응시킨 뒤 참조 위치에서만 치환한다. 표시 이름·유사 문구를 추측해 연결하지 않는다. 기존 정본과 모든 추가 선언, 그래프, 장소 조건을 한 프로젝트로 검증한다.
- **상태와 장소** — 퀘스트·인물·장소 키는 해당 개체, 관계 키는 세력, 아이템·결정·플래그 키는 동일 종류의 stateEntities 선언을 참조한다. 조건 검사와 결과 대입은 기존 문자열 값의 의미를 유지한다. world.locations와 scenario.locations는 동일한 장소 ID 공간을 사용한다. 추가된 장소와 이동 관계는 Phase 3에서 산문 재해석 없이 읽을 수 있다.
- **저장과 복구** — 소유자가 채택하면 정본 추가분과 그래프를 한 번의 IndexedDB 트랜잭션으로 기록한다. 기존 버전·출처와 충돌하는 응답은 거절한다. 예전 프로젝트는 읽을 때 수정하지 않는다. 기존 그래프에만 있던 아이템·결정·플래그 키는 종류별로 해석하며, 새 제안을 채택할 때 명시적 목록에 등록한다. 유형 간 ID 충돌에는 재현 가능한 새 ID를 부여한다. 기존 이야기, 편집 내용과 레이아웃은 단순 열기나 생성 실패로 변경되지 않는다. [포맷과 레거시 규칙](DATA_SCHEMA.md)
- **오류 진단** — 유형별로 접힌 결과를 열면 소유 노드·연결·퀘스트, 정확한 필드 경로, 문제 ID, 기대 유형과 확인된 실제 유형을 볼 수 있다. 정규화 가능한 참조 오류에 한해, 해당 탭에서 새 개체를 명시적으로 등록하거나 올바른 ID를 선택하고 로컬 재검증할 수 있다. 성공해도 제안 채택은 별도다. 실패 실행의 사용량은 남기고, 거절 초안은 IndexedDB·로그에 쓰지 않는다. 중복 선언, 잘못된 응답 구조, 고정 사실 충돌, 그래프 단절 등은 이 재연결 절차로 고칠 수 없다.

## 소유자 확인과 Phase 3 경계

오프라인 설정 확인에서 chatkhu·gpt-6.2-sol·responses, 120초, 일반 6,000·시나리오 12,000토큰, 최대 시도 1회를 확인했다. 현재 셸은 파일과 다른 ChatKHU 키를 갖고 있으므로 소유자가 인증에 성공한 셸의 설정으로 실행한다. 개발·자동 검증 중 ChatKHU 생성 및 직접 OpenAI 호출은 0회다. 실제 계정과 렌더링된 브라우저에서 수정 후 생성 성공 여부는 PENDING이다.

기존 브라우저 프로필과 주소에서 **잊혀진 달**의 승인 이야기를 열고, 표준 3장·분기·복수 결말 설정으로 요청 1회를 직접 시작한다. 인물 소속, 퀘스트 선행 조건, 결말 효과, 장소 이동을 검토한다. 필요하면 유료 재요청 전에 로컬 참조 수정을 사용한다. 명시적으로 채택·검증·승인한 뒤 새로고침해 다시 연다. Phase 3의 입력 조건은 현재 원천 이야기, 승인된 시나리오, 유효한 장소 ID와 이동 제약이다. 실제 이야기에서의 의미 적합성과 소유자 승인이 남아 있다. [실행 절차](../README.md#승인된-이야기의-인물세력과-시나리오-참조-확인) · [TDD 증거](TDD_EVIDENCE.md)
