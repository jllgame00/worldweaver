# Phase 2.3 시나리오 생성과 진행 신뢰성

**오프라인 구현·회귀 PASS. 실제 ChatKHU 생성과 브라우저 검증 PENDING.** 표준 시나리오의 요청 예산은 1회다. 이번 작업에서 실제 모델 호출은 0회이며 크레딧 사용은 0이다.

## 장애 조사

소유자가 보고한 요청은 Responses에서 5,528토큰(추론 0)을 수신했다. 실행 경로는 `nodes-39f4a8905245563daebd0bb3563cb693`에서 `nodes-67926ef1c46e51e5a3076516954dea95`까지였고, `quests-e8399a39ad5458cf8570326abf311652` 선행 조건이 남았다. 당시 코드에서 정규화된 후보를 회신하는 경로는 일부 참조 오류로 제한됐고, 진행 실패 시 저장한 것은 실행 영수증이었다. 저장소의 진단 자료에서 해당 ID의 그래프를 찾지 못했다. 소유자의 브라우저 원본도 확보하지 못했다. 당시 어느 사건의 효과나 연결이 잘못됐는지는 미확정이다.

코드와 테스트에서 확인된 결함은 퀘스트 노드에서만 완료를 판정하던 동작이다. 나중에 물건을 얻어도 활성 퀘스트가 완료되지 않았다. 또한 시작 노드의 진입 조건, 갈림길에서 다른 출구가 있던 경우의 영구적으로 막힌 출구, 활성화 이전의 완료 대입 등을 충분히 구분할 수 없었다. 생성 지침에는 상태 적용 순서와 이를 따르는 구체적 예시가 부족했다. 실패 후 정본을 보존했지만 편집자가 진행 문제를 고쳐 재검증할 수 있는 원본을 돌려주지 않았다.

## 생성·편집 계약

1. 현재 승인된 내러티브, 고정 사실·소재와 유형별 개체 목록을 읽는다. 제공자는 창작 내용, 로컬 ID, 선택·연결, 선언된 조건과 효과를 한 번에 제안한다. 지침에는 선택 퀘스트 수락, 뒤이은 인장 발견, 의회 합류, 즉시 산회 또는 증거 공개의 두 결말이 포함된다.
2. 기존 컴파일 단계가 로컬 ID를 정본 ID로 대응시키고 조건과 연결을 정규화한다. 이후 도메인 도구가 개체·장소·퀘스트 소유권, DAG와 경로별 상태를 검사한다. 승인된 이야기와 편집 중인 정본은 생성 실패로 교체되지 않는다.
3. 시작은 빈 상태다. 노드 진입 전에 방문·상태 조건과 퀘스트 선행 완료를 검사한다. 퀘스트 노드가 자기 퀘스트를 활성화하고 노드의 효과를 적용한다. 활성 퀘스트의 실패·완료를 판정한 뒤 출구 조건을 확인한다. 연결의 효과와 그에 따른 퀘스트 정산 후 도착 노드의 진입을 검사한다. 같은 단계에서 실패가 우선하며 완료·실패는 최종 상태다. 빈 완료 조건은 기존의 단발성 퀘스트 수행 의미를 유지한다. 작성된 완료 조건이 있으면 모두 같은 경로에서 충족해야 한다.
4. 분기마다 방문 및 상태 이력을 독립적으로 유지한다. 필수 장면마다 가능한 플레이 이력이 하나 있어야 한다. 서로 배타적인 장면을 한 번에 방문할 필요는 없다. 선택 퀘스트를 건너뛰어도 메인 진행과 적어도 한 결말이 가능해야 한다. 선택 퀘스트 전용 결말도 허용된다. 탐색 상한 2,048에 도달하면 승인을 차단한다.
5. 실패한 진행 조건에는 장면·퀘스트·연결 이름, 현재값·필요값, 실행 가능한 경로, 후보 원천과 필드 경로를 표시한다. 모든 유입 경로가 같은 원인을 가리킬 때만 하위 오류를 묶는다. 특정 값의 공급 후보는 해당 이력에서 실제 실행됐다는 증거와 구분한다.
6. 복구 가능한 전체 생성 제안은 별도 로컬 진단 저장소에 최초 원본을 보관한다. 같은 그래프 편집기로 연결, 선행 조건, 상태 효과와 결말을 작업 사본에서 수정한다. 로컬 검증 성공 후 원본 대비 변경을 확인하고 명시적으로 수락하면 초안이 저장된다. 승인에는 현재 리비전의 검증과 소유자 검토가 별도로 필요하다.

## 소유자 검증과 다음 단계

1. 기존 프로젝트를 저장했던 브라우저 프로필·주소와 인증에 성공한 PowerShell을 사용한다. 저장소에서 `.\.venv\Scripts\python.exe -m scripts.chatkhu check`로 설정을 확인하고 `.\scripts\start-dev.ps1`을 실행한다.
2. **잊혀진 달**의 승인 이야기를 열고 **Scenario Studio**에서 표준 3장·분기·복수 결말을 선택한다. ChatKHU, gpt-6.2-sol, Responses, 120초, 6,000/12,000토큰, 최대 시도 1회를 확인한다. 소유자가 비용을 승인하면 **Generate scenario**를 한 번 누른다.
3. 거절되면 **Rejected proposal editor**에서 실제 차단 경로, 퀘스트 목표의 공급 사건, 상태 값과 조건의 순서를 확인한다. 수정 사항을 저장하고 **Revalidate edited proposal**로 다시 검사한다. 진단 원본을 보관하려면 **Rejected scenario file → Export original rejected graph**를 선택한다.
4. 통과한 제안은 변경과 선택의 대가를 검토한 뒤 **Accept proposal**로 저장한다. **Validate scenario**에서 결말별 경로를 확인하고 고정 사실과 이동 조건을 검토한 후 **Approve scenario**를 선택한다. 같은 주소에서 새로고침하여 재열기와 승인 상태를 확인한다. 종료는 시작 터미널에서 Ctrl+C.

원본 보관 단위는 프로젝트별 한 건이며 작업 사본은 현재 화면에 있다. 원본이 오래되면 내보낼 수 있고 다른 리비전에 적용할 수 없다. 잘린 응답, 잘못된 전송 구조, 고정 사실 충돌처럼 정본 후보를 구성할 수 없는 실패는 그래프 편집 대상으로 제공되지 않는다. 로컬 저장소 사용 불가 시 현재 탭에서 원본을 내보낼 수 있다. 선택의 서사적 가치와 실제 모델의 생성 성공률은 합성 테스트로 측정하지 않았다. Phase 3 진입에는 소유자가 확인한 최신 승인 시나리오와 올바른 장소·이동 요구사항이 남아 있다.
