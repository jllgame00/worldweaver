# Phase 5D · 프로젝트 백업 복원

**로컬 GREEN 통과.** 시작 시 `feature/product-polish`의 작업 트리는 깨끗했다. HEAD `34aad6d7552dc033e8fb945a6dcaa7e9736998ce`의 변경 파일은 `frontend/src/projectRestore.test.tsx` 하나다. 부모는 5C GREEN `ae5979a362ce5e46b9a9192b07f1ba7c9eaaa422`이다. 원본 테스트 파일을 그대로 유지했다. 5D 구현 커밋은 소유자 대기 중이다.

## 복원 시 보존되는 데이터

- **미리보기.** 같은 ID의 파일을 선택하면 DB에서 현재 행을 다시 읽는다. 현재 저장 시각과 파일 수정 시각을 구분해 보여 주고, 제목·리비전·승인과 소재·고정 설정·스토리·장면·퀘스트·엔딩·인물·세력·장소·지도·검증 기록을 비교한다. 변경은 ID별 추가·삭제·수정으로 구분하고 바뀐 필드와 순서도 확인할 수 있다. 취소하거나 한영 표시를 전환하는 동안 정본 쓰기는 0회다.
- **저장 경쟁.** 확인 시 `restoreProject`가 동일한 읽기·쓰기 트랜잭션에서 현재 행의 토큰을 검사한다. 토큰이 다르거나 행이 없으면 중단한다. 다른 탭의 재저장이 내용·시각·리비전까지 같아도 거부한다. 열린 미리보기에서 원래 파일을 유지한 채 최신본과 다시 비교하거나, 최신 프로젝트를 열 수 있다. 재비교 뒤에도 명시적으로 복원을 눌러야 한다.
- **원자적 복원.** 기존 DB 이름을 유지하고 버전 2에서 `previousProjects` 저장소만 추가한다. 기존 `projects` 행을 다시 쓰는 마이그레이션은 없다. 복원은 직전 정본을 별도 저장소에 기록하고, 기존 ID에 새 저장 토큰과 현재 리비전 + 1로 백업을 반영한다. 둘 중 어느 쓰기에서든 중단되면 이전 두 저장소의 상태로 돌아간다. 화면은 트랜잭션 완료 후에만 성공을 표시한다.
- **승인.** 가져온 구조·유형·참조와 최종 승인 주장의 출처·지문을 검사한다. 누락된 필수 실행 기록이나 모순된 최종 승인 주장은 거부한다. 유효한 스토리 승인은 유지하고 오래된 스토리는 초안으로 연다. 시나리오·지도·프로젝트 최종 승인 및 로컬 시나리오 검사 영수증은 새 검증과 승인이 필요하다. 보고서·수리 결정은 원래 지문과 함께 과거 이력으로 남으며, 같은 설계 지문이라도 가져온 제안을 바로 실행할 수 없다.
- **별도 사본.** 새 프로젝트 ID에 생성 전용 쓰기를 사용한다. 내부 인물·장소·장면·연결 ID와 창작 문구는 유지한다. 생성한 ID마저 충돌하면 그 행을 보존하고 다시 선택하도록 안내한다. 같은 제목의 프로젝트는 목록에서 보조 ID로 구분할 수 있다.
- **보관 한도.** 직전 정본 한 개를 프로젝트별로 보관한다. 일반 저장과 새로고침 후에도 다운로드할 수 있고 다음 성공한 복원에서 교체된다. 다운로드 시작과 복원 성공을 구분하며, 파일 선택 창에서 저장을 완료했는지는 앱이 알 수 없다. 가져오기 한도는 파일당 16 MiB다. 여유 공간 부족이나 다른 탭이 구버전 DB 연결을 계속 보유한 경우 공간을 확보하거나 해당 탭을 닫은 뒤 다시 시도한다. 프로필·주소가 바뀌거나 사이트 저장소를 잃으면 로컬 직전본도 사용할 수 없으므로 장기 백업은 별도 파일로 보관한다. 자유 입력·거절 제안·지도 작업본의 별도 브라우저 저장소는 정본 JSON의 범위 밖이다.

## 테스트 근거

루트에서 `npm.cmd --prefix frontend test -- projectRestore.test.tsx --reporter=verbose`를 실행했다. 구현 전 종료 코드 1, 구현 후 종료 코드 0이었다.

| 원본 테스트 | RED 관찰 | GREEN에서 확인한 결과 |
|---|---|---|
| D1 previews a same-ID backup and its changes without writing either version | 미리보기 없음 | 현재·백업의 제목과 소재를 대조하고 저장 행 전체 보존 |

| D3 commits the reviewed backup once and offers the exact previous project as recovery JSON | 미리보기 없음 | 새 토큰·리비전, 안정된 ID·참조, 재열기 후 다운로드 JSON이 직전 정본과 일치 |

## 소유자 확인

1. 별도 브라우저 프로필을 준비한다. 저장소 루트의 PowerShell에서 `npm.cmd --prefix frontend run dev -- --port 48572 --strictPort`를 실행하고 해당 프로필에서 `http://127.0.0.1:48572`를 연다. 이 절차에는 백엔드와 API 키가 필요 없다.
2. **프로젝트 → 새 프로젝트**에서 `복원 연습`을 만든다. **이야기 소재 → 소재 직접 편집**에서 `첫 수문`을 추가하고 **저장 완료**를 확인한다.
3. **검증 에이전트 → 저장된 프로젝트 JSON 내보내기**로 파일을 보관한다. 파일의 프로젝트 ID를 확인한다. **이야기 소재**에 `두 번째 수문`을 추가해 저장한다.
4. **프로젝트 → 프로젝트 JSON 가져오기**로 3번 파일을 고른다. 미리보기에서 제거될 `두 번째 수문`을 확인한 뒤 **취소**한다. 프로젝트를 다시 열어 두 소재가 모두 남는지 본다.
5. 첫 탭에서 프로젝트 목록으로 돌아가 같은 파일의 미리보기를 다시 연다. 같은 프로필의 두 번째 탭에서 같은 주소와 프로젝트를 열어 `세 번째 수문`을 추가하고 **저장 완료**를 확인한다.
6. 첫 탭에서 **기존 프로젝트 복원**을 누른다. 다른 탭의 저장 안내를 확인한다. **최신 저장본과 다시 비교**를 눌러 `세 번째 수문`까지 표시되는지 확인한 뒤 **기존 프로젝트 복원**을 다시 누른다.
7. **복원 직전 프로젝트 JSON 다운로드**를 눌러 새 파일을 열고 세 소재와 기존 ID를 확인한다. 복원된 현재 프로젝트에는 `첫 수문`만 남아야 한다.
8. **프로젝트 → 프로젝트 JSON 가져오기**에서 3번 파일을 다시 선택하고 **별도 사본으로 가져오기**를 누른다. 프로젝트 목록에서 같은 제목 아래 두 ID를 확인한다. 새 ID의 사본에만 소재 하나를 추가해 저장한다.
9. 새로고침해 두 프로젝트를 각각 열고 소재가 서로 구분되는지, 기존 ID 프로젝트에서 직전본을 다시 다운로드할 수 있는지 확인한다. 테스트 서버는 실행한 터미널에서 Ctrl+C로 종료한다.

권장 소유자 구현 커밋은 `feat(recovery): restore reviewed backups with atomic conflict protection`이다.
