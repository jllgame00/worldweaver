# 세계 설정 검증과 수리

**Quick Check는 공급자 키 없이 사용할 수 있다.** 참조와 지도는 브라우저에서 검사하고, 시나리오가 있으면 로컬 FastAPI에서 실제 플레이 상태를 탐색한다. 개발 서버 두 개를 모두 실행한다.

## 기존 프로젝트로 확인하기 · 0크레딧

1. 저장소 루트에서 PowerShell로 `.\scripts\start-dev.ps1`을 실행한다. 기존 프로젝트를 보관한 브라우저 프로필에서 `http://127.0.0.1:5173`을 연다.
2. **Projects → Open**에서 **잊혀진 달**을 연다. **Verification Agent → Export saved project JSON**으로 수정 전 백업을 저장한다. 같은 이름의 파일이 있으면 새 파일명을 쓴다.
3. **Narrative Studio**에서 선택한 이야기와 승인 상태, **Scenario Studio**에서 장면·퀘스트·엔딩과 현재 검증 상태, **World Atlas**에서 저장된 지도와 작업 제안·승인 상태를 확인한다. 과거 진단본에는 지도가 없으므로 실제 화면의 시드와 상태를 기준으로 삼는다.
4. **World Bible**의 **Record type**에서 Character, Faction, Location을 차례로 선택한다. 이름으로 검색하고 참여 장면, 퀘스트, 지역, 이동 경로를 살핀다. **Related records** 목록과 관계 그래프는 같은 ID를 선택한다. 그래프의 이동·확대·축소·**Fit graph**를 사용해 본다.
5. **Open in …**으로 원래 편집기를 열고 돌아온다. **Edit record → Preview change**에서 수정 전후 값과 직접·간접 참조, 재검토할 승인과 검사 기록을 확인한 뒤 **Cancel**을 누른다. 고정 사실에는 별도 **Edit locked fact → Preview change → Apply fact edit** 절차가 있다.
6. **Verification Agent → Quick Check → Run Quick Check**를 누른다. 실행 계획과 도구별 결과를 확인한다. 결과가 `skipped` 또는 `incomplete`이면 이유를 읽는다. 서버 연결 실패가 있으면 서버를 복구하고 새 검사를 실행한다.
7. 발견 사항의 설명과 **Evidence and field paths**를 펼친다. 장면이나 장소 이름을 눌러 World Bible로 이동한다. **Review this record**를 누르면 해당 ID가 선택된 **Targeted Review**로 돌아온다. 프롤로그에 미래 장면 방문이 필요하면 현재 상태와 필요한 장면 이름을 비교한다.
8. 수리 실험은 별도 합성 프로젝트에서 한다. 루트에서 `node frontend/scripts/verification-campaign.mjs --demo-only`를 실행한다. **Projects**로 돌아가 JSON 가져오기에서 `.scratch/phase4-synthetic-route-repair.json`을 선택한다. 이 파일에는 실제 경로보다 10 km 긴 경로 하나가 있다. 기존 파일이 있으면 명령은 그 파일을 보존한다. 가져온 복사본의 시나리오·지도 승인은 직접 재검토해야 한다.
9. 복사본에서 **Run Quick Check** 후 거리 불일치의 **Prepare repair**를 연다. **Reject proposal**을 누르면 원래 거리가 유지되고 거절 이력이 저장된다. 다시 **Prepare repair → Simulate on isolated copy**를 누른다. 전후 거리, 영향받는 장소, 도구별 결과와 승인 상태를 비교한다.
10. 이 시점에 새로고침하고 복사본을 다시 열어도 이력에서 비교안을 열 수 있다. 수락하려면 확인란을 체크하고 **Accept repair and download recovery JSON**을 누른다. 다운로드한 JSON으로 수리 직전 상태를 복구할 수 있다. 저장한 정본을 다시 검사한 Full World Review가 이력에 추가된다. 같은 오류가 사라졌는지, 여전히 승인 대기나 다른 오류가 있는지 확인한다.
11. **Export report Markdown**, **Export findings JSON**, **Export saved project JSON**을 각각 저장한다. 새로고침 후 다시 열어 수락·거절 이력과 수정한 거리를 확인한다. **Revalidate**는 화면에서 선택한 보고서 범위로 새 결정적 검사를 실행한다. 작업이 끝나면 시작 터미널에서 Ctrl+C를 누른다.

## 선택 사항 · ChatKHU 요청 한 번

1. 실행 중인 개발 서버를 종료한다. 기존 로컬 `.env`에서 `WORLDWEAVER_PROVIDER=chatkhu`, `CHATKHU_MODEL=gpt-6.2-sol`, `CHATKHU_API=responses` 및 이미 설정한 서버 측 키를 사용한다. 키는 UI나 프로젝트 파일에 입력하지 않는다. 다시 `.\scripts\start-dev.ps1`을 실행한다.
2. **World Bible**에서 검토할 기록을 선택하고 **Review this record → Run Targeted Review**를 누른다. 더 넓게 보려면 **Full World Review → Run Full World Review**를 사용한다. 여기까지 모델 요청은 0회다.
3. 완료된 결정적 보고서에서 **Review semantic evidence**를 누른다. 공급자·모델, 선택한 범위와 리비전, 실제 제출할 발췌, 최대 1회, 출력 상한(서버 설정과 1,600토큰 중 작은 값), 가격 확인 가능 여부를 읽는다.
4. 비용과 발췌 공개에 동의할 때만 **Authorize one live review**를 한 번 누른다. 성공·실패 영수증과 제공된 사용량을 확인한다. 재요청에는 별도 동의가 필요하다. 전송 후 취소하면 실제 과금 여부가 미확인으로 남을 수 있다.

## 실행 모델

| 단계 | 기록하거나 수행하는 일 |
|---|---|
| 스냅샷과 범위 | 정본을 복제하고 의미 있는 입력의 SHA-256을 계산한다. 레이아웃 좌표·검증 이력·저장 리비전은 체크섬에서 제외한다. 대상 모드는 정본 참조 그래프에서 필요한 범위를 도출한다. |
| 도구 계획과 실행 | 허용 도구는 `schema`, `references`, `sources`, `progression`, `atlas`, `coverage`다. Quick은 앞의 다섯 도구를 계획한다. Targeted는 의존 도메인을 선택하고 Full은 여섯 도구를 계획한다. 실행하지 못한 이유도 결과에 남긴다. |
| 증거 | 중복·오류 종류·필드 경로, 실제/요구 상태, 도달 가능한 엔딩 경로, 공간 오류와 좌표를 저장한다. 진행 도구는 방문 조건·퀘스트·효과를 실제 경로별로 탐색한다. 지리는 실행 가능한 물리 이동 요구와 명시적 지리 요구를 검사한다. 지하 층, 수로, 도로, 해로를 기존 Atlas 규칙으로 해석한다. |
| 의미 검토 | 선택한 발췌와 고정 사실을 데이터로 전달한다. 출력의 자료형·ID·인용문 일치를 서버와 클라이언트에서 확인한다. 검토한 텍스트의 불확실성과 편집 제안은 별도로 남는다. 명시적으로 제안한 관계는 인용된 양 끝점이 있을 때만 그래프에 표시한다. |
| 수리 | 규칙·필드·정본 ID에 묶인 변경을 임시 사본에서 검사한다. 허용된 작업에는 상태 조건과 참조의 교체, 전이 끝점 수정, 서술 수정, 소유자 지리 조건 끝점 수정, 기존 경로의 길이·경유 셀 복원이 있다. 경로의 ID, 양 끝점, 모드는 보존한다. 수정 의미가 불명확하면 소유자가 값을 정한다. |
| 동의와 저장 | 실행당 수리 제안은 최대 2건, 묶음당 12개 필드다. 거절·실패한 요청도 예산에 포함된다. 원래 값, 리비전, 지문을 다시 확인하고 묶음 전체를 시뮬레이션한다. 소유자가 선택한 안만 한 정본 트랜잭션에 반영한다. 변경된 도메인의 승인과 하위 도메인의 출처 버전을 재검토한다. |
| 재검증과 최종 승인 | 수락 후 저장한 정본에 Full 검사를 새로 실행한다. 수리 후 자동 검사는 추가 수리를 시작하지 않는다. 전체 검증이 통과하고 상위 승인이 현재일 때만 최종 승인 확인란이 나타난다. 소유자의 **Recheck and approve this design**이 전체 검사를 다시 실행한다. |

같은 주소의 IndexedDB에서 저장 토큰으로 여러 탭의 경쟁 쓰기를 검사한다. 프로젝트 JSON에는 최근 12개 검증 보고서, 실행별 도구 상태, 최대 500개 소견과 64개 엔딩 증거 경로, 제안과 결정이 들어간다. 소견 보관 상한을 넘으면 생략 개수를 표시하고 좁은 범위에서 다시 검사한다. 이전 버전 JSON에는 이 필드가 없어도 된다. 자세한 규칙과 측정 결과는 [스키마](DATA_SCHEMA.md), [캠페인](VERIFICATION_CAMPAIGN.md), [Phase 4 보고서](PHASE_4_REPORT.md)에 있다.

## 판정의 경계

구조 검사는 참조, 명시한 규칙과 가능한 경로를 다룬다. 자연어로만 쓴 역사·동기·세계 법칙의 의미, 빠진 창작 정보, 여러 설정 중 어느 쪽을 살릴지는 편집 판단으로 남는다. 의미 검토는 회당 최대 64개 발췌와 입력 예산을 사용하며 전 작품을 읽었다는 판정을 내리지 않는다. 파일과 화면의 구조적 검증을 통과해도 최신 소유자 프로젝트의 창작 승인과 실제 브라우저 조작 품질은 별도로 확인한다.
